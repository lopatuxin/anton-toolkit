## 🚀 Как этим пользоваться

Есть **три способа** запустить инструмент:

### 1. Триггер-фраза (обычный диалог)

Просто пишешь по-русски, Claude сам подберёт скилл:

```
> закоммить изменения                    → запустится commit
> почему API тормозит?                   → запустится debug
> разверни сервис в докере               → запустится агент devops
> вот задача, реализуй                   → запустится task-build
> проанализируй мой канал                → запустится yt-my-channel
> спроектируй систему                   → запустится system-designer
```

> ⚠️ Часть скиллов **запускаются только по slash-команде**, без авто-триггера (`disable-model-invocation: true`): личный `film`, курсовые (`lesson`, `roadmap`), все `yt-*`, учитель `teach` и `mr-review`.

### 2. Slash-команда (явный вызов)

```
> /commit
> /improve-plugin
> /feature-planner
> /dnevnik
> /task-build
```

### 3. Делегирование агенту

Агенты вызываются Claude'ом автоматически (если задача под их профиль), либо явно:

```
> вызови code-reviewer на этот PR
> протестируй фичу через qa-engineer
```

> 💡 **Триггеры — не источник истины.** Полный список фраз и нюансов — в YAML-frontmatter каждого `SKILL.md` / `<agent>.md`. Этот README — навигация.

### Анатомия одного плагина

```
plugins/<plugin-name>/
├── .claude-plugin/
│   └── plugin.json              # name, version, description
├── skills/                      # скиллы — запускаются в основном диалоге
│   └── <skill-name>/
│       ├── SKILL.md             # инструкции для модели + YAML-frontmatter (описание, флаги)
│       └── references/          # файлы только этого скилла (шаблоны, чеклисты)
├── agents/                      # subagent'ы — автономные исполнители
│   └── <agent-name>.md          # ТОЛЬКО агенты: любой другой .md здесь станет агентом-призраком
├── references/                  # общие референсы плагина, цитируются как ${CLAUDE_PLUGIN_ROOT}/references/...
├── hooks/                       # hooks.json + скрипты — то, что обязано выполняться всегда
└── workflows/                   # сценарии оркестрации агентов (если есть)
```

Slash-команда — это скилл с `disable-model-invocation: true`; отдельной папки `commands/` больше нет.

| | **Skills** | **Agents** |
|---|------------|------------|
| **Где работают** | В основном диалоге | В изолированном sub-контексте |
| **Что делают** | Ведут интервью, генерируют документы, оркестрируют | Выполняют одну задачу под ключ |
| **Когда вызывать** | По триггер-фразе или `/<имя>` | Когда нужно делегировать «закрытую» задачу |
| **Пример** | `feature-planner` (интервью + план) | `java-dev` (пишет код по плану) |

## 🛠 anton-toolkit

> **Инженерный швейцарский нож.** Оркестратор задачи `task-build` — от плана до проверенной вживую фичи одним прогоном, коммиты, ревью с воротами в конце хода и перед коммитом, дебаг, devops, dev-агенты под Java/Kotlin/Python/Go/Frontend, соглашения по языкам, которые подгружаются сами, хуки и end-to-end QA. Плюс параметрическое проектирование деталей и механизмов во FreeCAD.

**Как устроена работа с кодом.** Мелкие правки основная сессия делает сама: при касании `.kt`, `.go`, `.rs`, `.py`, `.java`, `.ts/.tsx` автоматически подгружается скилл-соглашение языка (`kotlin-conventions`, `go-conventions`, `rust-conventions`, `python-conventions`, `java-conventions`, `frontend-conventions`) плюс общие принципы `karpathy-principles` — это скрытые скиллы-знания, в меню `/` их нет. Dev-агенты — для крупных самостоятельных задач и готовых планов; тесты к своей правке пишет тот же агент. Ревью — до того, как результат увидит пользователь. В репозитории с файлом `.claude/review-gate` хук `Stop` не даёт Claude закончить ответ, пока файлы кода, которые он сам правил в этой сессии, не прошли `code-reviewer` (правки самого пользователя в IDE не считаются — хук ведёт список тронутых файлов по сессии); блокеры Claude чинит сам, остальные замечания перечисляет в ответе. Там же хук `PreToolUse` не пропустит `git commit` с непроверенным кодом, когда коммитит сам Claude. Отметку о просмотренном состоянии (`.git/anton-toolkit-review-mark`) ставят `code-reviewer` и `mr-spec-reviewer`; сознательный обход коммита — `ANTON_SKIP_REVIEW=1`. Хуки (`hooks/hooks.json`): `gofmt` после правки `.go` и учёт тронутых файлов, отметка ревью по завершении ревьюера, ворота на конец хода и на `git commit`.

### Skills

<details open>
<summary><b>🏗 task-build</b> — задача от плана до проверенной вживую фичи</summary>

Оркестратор разработки одной рабочей задачи: ведёт её от постановки до кода, который отревьюен, покрыт тестами и проверен на живом стенде. Планирование отдаёт `feature-planner`, дальше сам определяет стек каждого затронутого модуля по маркеру сборки (`pom.xml` → `java-dev`, `build.gradle.kts` → `kotlin-dev`, `pyproject.toml` → `python-dev`, `go.mod` → `go-dev`, `Cargo.toml` → `rust-dev`, `package.json` → `frontend-dev`) и запускает сценарий `workflows/task-build.js`: dev-агенты пишут код вместе с тестами (модули с зафиксированными в плане контрактами идут параллельно) → `code-reviewer` смотрит **готовый дифф целиком** → блокеры перед правкой проходят состязательную проверку, чтобы круг правок не запускался из-за придирки → до двух кругов правок → агент `devops` поднимает локальный стенд на свежей сборке → `qa-engineer` гоняет фичу вживую, его баги уходят обратно владельцу файла → финальное ревью ставит отметку для ворот.

Правится только `Critical`; `Warning` и `Info` возвращаются пользователю списком — что с ними делать, решает он. Отдельного тест-райтера в конвейере нет: тесты пишет тот же агент, что писал код. Коммит скилл не делает — показывает отчёт и оставляет дерево изменений на просмотр.

**Триггеры:** `"реализуй задачу"`, `"собери задачу"`, `"сделай фичу"`, `"вот тикет, реализуй"`, `/task-build`

> ⚠️ Не путать с `feature-planner`: тот только планирует. `task-build` планирует **и строит**.
</details>

**Пример:**

<details>
<summary><b>📋 feature-planner</b> — планирование фичи через интервью</summary>

Проводит интервью по требованиям **ДО** реализации. На выходе — детальный план, по которому потом работают dev-агенты без уточнений. План ложится в `docs/plans/`, а если CLAUDE.md проекта называет папку фаз (личные проекты в хранилище) или папку задач (рабочие проекты в хранилище) — заметкой фазы или задачи туда.

**Триггеры:** `"спланируй фичу"`, `"распланируй фичу"`, `"продумай фичу"`, `"спроектируй фичу"`, `"уточни нюансы"`, `"вот тз"`, `/feature-planner`

> ⚠️ Не путать с `system-designer`: тот проектирует **систему целиком** (документация), а `feature-planner` готовит **одну фичу к имплементации**.

**Когда использовать:** перед стартом любой нетривиальной фичи — чтобы dev-агенты потом не задавали лишних вопросов.
</details>

<details>
<summary><b>📝 mr-review</b> — ревью ветки (MR) по документации</summary>

Скилл-команда: запускает агента `mr-spec-reviewer` в отдельном контексте (`context: fork`) и возвращает его отчёт — `файл:строка` + готовый текст замечания для MR. Сам не срабатывает (`disable-model-invocation: true`).

**Вызов:** `/mr-review [база-ветки | путь к докам | файлы]`

<details>
<summary><b>📐 freecad-design</b> — проектирование деталей и механизмов во FreeCAD</summary>

Работает через MCP-сервер `freecad` в той же запущенной копии программы, что открыта у тебя: ты говоришь, что нужно, скилл строит модель, ты сам смотришь её во FreeCAD, дальше правки. Модель всегда параметрическая — размеры вынесены в таблицу `Params`, поэтому «сделай на 5 мм выше» это одна цифра, а не пересборка, и менять её можно самому в интерфейсе. Скриншоты по умолчанию выключены.

Перед выбором размеров определяет способ изготовления и берёт правила под него: зазоры посадок и толщины стенок для печати, радиусы под фрезу и глубину кармана для фрезеровки, канавки и заходные фаски для токарки, зазор и катет для сварки, толщину листа и присадку для мебели. Умеет сборки с рабочими связями (шарнир, ползун, шестерни), привод по формуле от времени с прокруткой кадров, поиск пересечений по всему диапазону движения, прочностной расчёт CalculiX, чертёж TechDraw и экспорт STL/STEP/PDF. Файлы складывает в `C:\projects\FreeCAD\<деталь>\`.

**Триггеры:** `"спроектируй деталь"`, `"смоделируй во фрикаде"`, `"сделай кронштейн"`, `"поправь модель"`, `/freecad-design`

> ⚠️ Управляющие программы для станка (CAM, G-code) не делает.
</details>

<details>
<summary><b>🔚 close-session</b> — закрытие сессии записями</summary>

Вызывается в конце сессии в любом проекте, личном или рабочем. Находит карточку проекта (`kind: project`) по репозиторию и пишет в журнал проекта по короткой записи на каждое решение или тупик сессии: что выбрали, почему, что отвергли — только то, чего не видно по гиту и коду. Решений не было — журнал не трогает. Обновляет в карточке `next` (одно-два предложения) и `updated`. Строку в `Кто-я.md` сначала показывает и пишет после «да»; файл держит в 60 строках. Из заметок памяти этой сессии убирает то, что ушло в журнал и карточку. Единственный, кто пишет журналы и карточки проектов.

**Триггеры:** `"закрой сессию"`, `"закрываем сессию"`, `/close-session`
</details>

<details>
<summary><b>🔎 vault-search</b> — поиск по хранилищу Obsidian</summary>

Срабатывает сам из любого проекта, когда ответ зависит от записанного в хранилище `C:\projects\obsidian`: где стоит проект и что дальше, прошлое решение и его причина, план, заметка по теме. Без индекса и поиска по смыслу — обычными Grep/Glob/Read: сначала карточки проектов (`kind: project`) и заглавные заметки папок, потом поиск по основе слова (`памят`, а не «память» — поиск не знает русских окончаний; ё и е обе), с синонимами и английским термином в одном запросе. Сужает по месту (журнал — решения, фазы — планы, дата в имени файла), по тегам и обратным ссылкам; служебные папки пропускает, архив — только по запросу. Читает только найденные куски. Называет заметку-источник или честно говорит, что не нашёл и что искал. Как система работает сейчас — не из хранилища, а из её репозитория.

**Триггеры:** `"найди в хранилище"`, `"что у меня по Кузне"`, `"мы это уже решали"`, `"где заметка про"`
</details>

<details>
<summary><b>🎓 teach</b> — учитель для самостоятельной учёбы любой области</summary>

Учит **любой области** через **один сквозной проект**, который хозяин строит с нуля своими руками. Новый курс начинается с **разговора**: чего он хочет уметь в итоге, что уже знает, сколько у него времени. Дальше короткая **проверка уровня** вопросами, **поиск**, как эту область учат другие, и **программа** из небольших уроков, собранных в блоки: каждый урок — одна новая идея, добавленная в проект, и вытекает из предыдущего. Программа пишется в хранилище только после одобрения. **Код пишет только хозяин**: учитель объясняет простым языком на числах из проекта, ведёт вопросами, подсказывает по ступеням, где застрял, запускает и проверяет написанное — по одному пункту за раз. Урок закрывается, когда шаг проекта работает и хозяин объяснил своими словами почему; в конце — английские названия сделанного. **После каждого урока короткий разбор**: что получилось, что подтянуть по теме и по коду, стоит ли поправить программу (правка только с согласия). Без баллов и оценок. **Помнит между сессиями** заметку `Обучение <проект>` в папке учебного проекта.

**Вызов:** `/teach` (только командой, без авто-триггера)

> ⚠️ Учитель код не пишет и агентов не зовёт; карточку и журнал проекта ведёт `/close-session`.
</details>

### Agents

| Агент | Когда сработает | Что делает |
|-------|-----------------|------------|

| 🌐 **frontend-dev** | Крупная фронтовая задача: страница, фича, рефакторинг (`*.tsx`, `*.ts`, `*.css`, ассеты) | Пишет React/TS-код и тесты к нему; мелкие правки — основная сессия с подгруженными соглашениями. |

| 📝 **mr-spec-reviewer** | Только командой `/mr-review` — без триггер-фраз | Сверяет всю ветку (MR) с документацией проекта из хранилища Obsidian (для рабочих проектов — папка `Требования <проект>`) и выдаёт готовые тексты замечаний для MR: `файл:строка` + короткое сообщение без жаргона. Ищет и баги/безопасность, и нарушения контрактов из доки; дока же отсеивает ложные срабатывания. |
| 🧪 **test-writer** | Только по запросу: `"напиши тесты для X"`, поднять покрытие, переписать хрупкие тесты | Находит фреймворк и паттерны тестов проекта (JUnit/Kotest, `go test`, `pytest`, vitest), пишет в том же стиле. Тесты к своей правке dev-агенты пишут сами. |
| 🕵 **qa-engineer** | `"протестируй фичу"`, `"smoke-тест"`, `"протестируй перед мержем"` | End-to-end тест: API через `curl`, UI через браузерные инструменты сессии, выдаёт bug-report с маршрутизацией (backend bug → dev-агент языка модуля). |
| 🚢 **devops** | `"разверни проект"`, `"подними в докере"`, `"задеплой"`, `"логи контейнера"`; шаг «Стенд» в `task-build` | Dockerfile, compose с health-чеками и томами, nginx, CI/CD, диагностика не стартующего сервиса. Поднимает **локальный** стенд с пересборкой образов, чтобы тест шёл против свежего кода, и доказывает, что приложение отвечает. Шаблоны — в `references/`. Прикладной код не пишет, удалённые окружения не трогает. |

## 📓 lichnost

> Круг личного развития в Obsidian-vault: дневник → итоги недели, месяца, года → советы, которые проверяет следующий итог. Итоги попутно ведут портрет личности, цели и, раз в месяц, финансы из локальной базы приложения Финансов. Итог запускается сам по понедельникам из запланированной задачи приложения, дневник — по вечернему вопросу. `film` — отдельный кинокуратор. Кода не пишет.

### Skills

<details open>
<summary><b>📔 dnevnik</b> — дневник под диктовку</summary>

Записывает дневниковую запись в Obsidian-vault, форматируя сырые мысли в чистый Markdown-нот с именем по дате. Одна фраза — полноценная запись. Без анализа и советов.

**Вызов:** `/dnevnik`, «запиши в дневник», ответ на вечерний вопрос
</details>

<details>
<summary><b>💭 idea</b> — идеи и цели</summary>

Каждая идея — отдельный нот под `Личная/Идеи`, написанный как лёгкая документация (переформулировка для ясности, без выдумок). Новая или доработанная идея привязывается к цели, которой служит, или предлагается как новая цель. Цели — в `Личная/Цели.md`: поставить, достичь, снять. Идея, ушедшая в проект или цель, не висит черновиком: получает статус «стала проектом» со ссылкой на карточку.

**Вызов:** `/idea`, «поставь цель», «доработай идею»
</details>

<details>
<summary><b>🎬 film</b> — личный кинокуратор</summary>

Ведёт три нота: профиль вкуса, лог просмотренного с рецензиями и короткий шортлист рекомендаций (≤10 фильмов). Три потока: порекомендовать, залогировать просмотренный фильм, мигрировать старую заметку.

**Вызов:** `/film`
</details>

<details>
<summary><b>📈 itogi</b> — итоги с советами</summary>

Каскад: недельный итог читает дневник, журналы проектов и число коммитов, месячный — недельные итоги и финансы, годовой — месячные. Начинается с проверки прошлых советов, заканчивается не более чем тремя советами под цели и двумя-тремя вопросами; ответы уходят в портрет. Месячный итог ведёт ход целей.

**Вызов:** `/itogi неделя|месяц|год`; сам — `авто` по понедельникам
</details>

## 🏗 plugin-builder

> Конструктор плагинов для этого маркетплейса. `create-plugin` и `extend-plugin` работают **проактивно** (создать новое / расширить), `improve-plugin` — **реактивно** (точечная правка после инцидента).

### Skills

<details open>
<summary><b>✨ create-plugin</b> — создание плагина с нуля</summary>

Интервью → структура → `plugin.json` → первые скиллы/агенты → регистрация в `marketplace.json`.

**Триггеры:** `"создай плагин"`, `"нужен новый плагин"`, `"хочу плагин для"`, `"сделай плагин, который"`, `"создай инструмент"`

**Когда использовать:** когда нужного плагина ещё нет в `plugins/`.
</details>

<details>
<summary><b>➕ extend-plugin</b> — расширение существующего плагина</summary>

Добавляет новый скилл/агент/референс в уже существующий плагин **в свежей сессии** (когда не было инцидента — иначе используется `improve-plugin`).

**Триггеры:** `"добавь в плагин"`, `"допили скилл"`, `"расширь плагин"`, `"хочу в <name> добавить"`, `"нужно дополнить плагин"`

**Дискриминация:**
- Плагина ещё нет → `create-plugin`
- Плагин есть, инцидент в текущей сессии → `improve-plugin`
- Плагин есть, свежая сессия, хочу больше функционала → `extend-plugin`
</details>

<details>
<summary><b>🔧 improve-plugin</b> — точечная правка скилла/агента в этом маркетплейсе</summary>

Реактивная правка после инцидента: пользователь говорит «вот эта штука глючит, исправь» — скилл правит исходник в `plugins/`, бампит PATCH-версию, делает git push.

**Триггеры (только явные):** `"улучши плагин"`, `"обнови скилл"`, `"исправь агента"`, `"запомни это в плагине"`, `/improve-plugin`

> ⚠️ Не вызывается проактивно. Только когда пользователь явно попросил.

**Альтернативы:** для нового плагина — `create-plugin`, для расширения существующего — `extend-plugin`.
</details>

## 🎬 youtube-toolkit

> Полный набор для ведения русскоязычного IT/vibe-coding YouTube-канала.
> **Cadence:** 1 видео/неделя, ≤ 20 минут, **без Shorts**.

> 🆕 **v0.3.x+:** персистентная **база знаний канала** (`yt-knowledge-base`) — Obsidian-vault со всеми видео, транскриптами, метриками и классификацией top/fail. Остальные скиллы подтягивают её как контекст автоматически. Поверх базы работает агент-стратег `yt-strategist`, выдающий топ-5 идей на неделю. В v0.4.x добавлен `yt-montage` — монтажный лист из готового сценария.

### Skills

<details open>
<summary><b>🗄 yt-knowledge-base</b> — персистентная база знаний канала</summary>

Собирает и хранит на диске **полный датасет** по каналу: карточка каждого видео (metadata + транскрипт + классификация top/fail), который автоматически подгружается остальными yt-скиллами как контекст.

**Триггеры:** `"собери базу по моему каналу"`, `"собери базу знаний канала"`, `"обнови базу видео"`, `"обнови БД канала"`, `"база знаний канала"`, `"построй базу канала"`, `"пересобери базу видео"`

**Два режима:**
- **INIT** — полная сборка с нуля (все видео канала)
- **REFRESH** — инкрементально: новые видео + обновлённые метрики по существующим

**Когда использовать:** один раз для INIT, потом периодически REFRESH (например, раз в неделю перед планированием).
</details>

<details>
<summary><b>📊 yt-my-channel</b> — анализ собственного канала</summary>

Что работает на канале, что не работает, топ-видео, метрики, текущая динамика. Умеет парсить вставленные данные из YouTube Studio.

**Триггеры:** `"проанализируй мой канал"`, `"топ видео на моём канале"`, `"статистика канала"`, `"метрики моего канала"`, `"оцени мой канал"`

**Не путать с** `yt-competitors` — это про себя.
</details>

<details>
<summary><b>🔭 yt-competitors</b> — конкуренты и ниша</summary>

Два режима:
- **SINGLE** — разбор одного канала глубоко
- **BATCH** — скан ниши по каналам выше порога подписчиков

**Триггеры:** `"анализ конкурентов"`, `"анализ ниши"`, `"разбери канал X"`, `"что заходит в нише"`, `"сравни с конкурентами"`, `"тренды в нише"`
</details>

<details>
<summary><b>💡 yt-ideas</b> — генерация тем для видео</summary>

**⚠️ Hard requirement:** скилл откажется работать без отчёта от `yt-my-channel` или `yt-competitors` в контексте. Сначала собираем данные, потом идеи.

**Триггеры:** `"идеи для роликов"`, `"о чём снять"`, `"темы для видео"`, `"что снять следующим"`
</details>

<details>
<summary><b>📅 yt-content-plan</b> — контент-план / календарь</summary>

Календарь публикаций с учётом cadence (1 видео/неделю).

**Триггеры:** `"контент-план"`, `"расписание видео"`, `"календарь канала"`, `"контент на месяц"`, `"график выхода видео"`
</details>

<details>
<summary><b>🎬 yt-script</b> — сценарий ролика</summary>

Hook, акты, CTA, темп. Максимум 20 минут.

**Триггеры:** `"сценарий для видео"`, `"напиши сценарий"`, `"hook для видео"`, `"структура ролика"`, `"скрипт ролика"`
</details>

<details>
<summary><b>🎞 yt-montage</b> — монтажный лист</summary>

Превращает готовый сценарий в монтажный лист: что показывать на экране в каждый момент, b-roll / shot list. Faceless-визуал (без говорящей головы). Текст не пишет — потребляет готовый сценарий.

**Триггеры:** `"монтажный лист"`, `"распиши монтаж"`, `"что показывать в видео"`, `"раскадровка"`, `"b-roll лист"`, `"план монтажа"`
</details>

<details>
<summary><b>🔎 yt-seo</b> — название, описание, теги</summary>

Заголовок (A/B варианты), описание с таймкодами, теги.

**Триггеры:** `"название и описание"`, `"тайтл и теги"`, `"подбери название"`, `"опиши видео"`, `"теги для видео"`

**Что НЕ делает:** превью — это `yt-thumbnail`.
</details>

<details>
<summary><b>🖼 yt-thumbnail</b> — концепт превью</summary>

Идея превью: текст, композиция, цвет, эмоция. **Картинку не рисует** — это концепт, который ты потом нарисуешь сам или в инструменте.

**Триггеры:** `"превью для видео"`, `"обложка для видео"`, `"thumbnail концепт"`, `"что нарисовать на превью"`
</details>

<details>
<summary><b>🎯 yt-promo</b> — продвижение и лидген на канале</summary>

**On-channel only:** pinned-комменты, end-screens, CTA в видео и описании, воронка на сайт-визитку.
**Out of scope:** кросс-промо на других платформах (Telegram, Habr и т.п.).

**Триггеры:** `"продвижение канала"`, `"как раскрутить канал"`, `"лидген на канале"`, `"привлечь заказы"`, `"закреп под видео"`, `"end screen для видео"`
</details>

### Agents

| Агент | Когда сработает | Что делает |
|-------|-----------------|------------|
| ♟ **yt-strategist** | `"что снимать на этой неделе"`, `"топ идеи на неделю"`, `"стратег по каналу"`, `"yt-strategist"` | Читает базу `yt-knowledge-base` + свежие отчёты конкурентов из vault, синтезирует **топ-5 приоритетных идей** на неделю с обоснованием на данных. Отчёт сохраняется в Obsidian vault. Базу не модифицирует — за refresh отвечает `yt-knowledge-base`. |

| `feature-planner` vs `system-designer` | Planner — **одна фича** к имплементации. Designer — **система целиком** в документации. |
| `task-build` vs `feature-planner` | Build планирует **и строит** до проверенной вживую фичи. Planner только планирует и на этом останавливается. |
| `create-plugin` vs `extend-plugin` vs `improve-plugin` | New plugin / add to existing / fix after incident. |
| `yt-my-channel` vs `yt-competitors` | Свой канал / чужие. |
| `yt-seo` vs `yt-thumbnail` | Текстовая обвязка / визуальная обложка. |
| `dnevnik` vs `itogi` | Сырая запись дня / разбор периода с советами, портретом и целями. |

## 🔄 Типовые воркфлоу

### 🆕 Запуск новой фичи в проекте

```
1. /task-build                → один прогон на всю задачу:
     /feature-planner            план в диалоге, файл в docs/plans/ или в папку фаз или задач из CLAUDE.md
     dev-агенты по стекам        код + тесты (параллельно, если контракты в плане)
     code-reviewer               ревью готового диффа + состязательная проверка блокеров
     devops                      локальный стенд на свежей сборке
     qa-engineer                 end-to-end проверка, баги — обратно владельцу файла
     code-reviewer               финальная дельта + отметка ревью
2. (смотришь отчёт: блокеры, Warning/Info, открытые вопросы)
3. /commit                    → коммит на русском
```

## 🛠 Поддержка и развитие

### Где править

| Что | Чем |
|-----|-----|
| Новый плагин | `/create-plugin` (из `plugin-builder`) |
| Новый скилл/агент в существующем плагине | `/extend-plugin` (из `plugin-builder`) |
| Точечная правка скилла/агента после инцидента | `/improve-plugin` (из `plugin-builder`) |

> ⚠️ **Не редактируй** руками файлы в `~/.claude/plugins/cache/` — это read-only кэш, изменения затрутся. Реальный источник — этот репозиторий, путь зависит от машины. На текущей машине: `~/.claude/plugins/marketplaces/anton-toolkit-marketplace/` (он же — git working copy).

### Версионирование

Каждая правка плагина → **bump PATCH** в `plugins/<name>/.claude-plugin/plugin.json`. Без bump'а маркетплейс не подтянет изменение на других машинах.
